# Plan

## Estrategia

Se reutiliza el CRUD de proyectos y el almacenamiento de imágenes que ya existen en el backend (`PortfolioProjectsAdminController`, `PortfolioProjectService`, tablas `portfolio_projects` y `portfolio_project_images`), y se completa la capa faltante: sesión `WebSession` para el único administrador, filtro propio de autorización dual para no romper SgInfra, seed idempotente de ArgentiCommerce y UI de administración bajo el prefijo `/portfolio`.

El orden es: contrato de autenticación y arranque en backend, seed independiente, rutas y login en frontend, panel CRUD con imágenes, pruebas y documentación, integración en `main` —incluyendo la base de autenticación que hoy está en el working tree—, despliegue y verificación HTTPS. Backend y seed pueden avanzar en paralelo; el panel depende del contrato de sesión y de las rutas; la verificación final depende de todas las piezas y del estado real de producción.

## Contratos y decisiones

- **Sesión `WebSession` de WebFlux, sin `HttpSession`.** No se usa `JSESSIONID`, `AuthenticationWebFilter`, `SecurityContextRepository` ni form login. El `AuthController` autentica contra `PORTFOLIO_ADMIN_PASSWORD` o el hash BCrypt, escribe un atributo de sesión, lo lee en `GET /session` y lo elimina junto con la sesión en `POST /logout`. Se rota el identificador de sesión al autenticar para evitar fijación.
- **Cookie compatible con el subpath.** La cookie se llama `SESSION` (default de WebFlux, configurada explícitamente), es `HttpOnly`, `SameSite=Lax` y `Path=/`. El navegador ve `/portfolio/api/...` y Nginx reescribe a `/api/...`; una cookie con `Path=/api` no se enviaría bajo `/portfolio` y queda descartada. `Secure` se activa cuando el scheme es HTTPS; `server.forward-headers-strategy=framework` permite que `X-Forwarded-Proto: https` se reconozca detrás de Nginx. En HTTP local la cookie funciona sin `Secure`.
- **Spring Security no intercepta.** `SecurityConfig` se reduce a `permitAll`, CSRF deshabilitado, sin form login y sin httpBasic. No hay matcher de `/api/admin/**` en la cadena. La autorización real de proyectos vive en un `WebFilter` propio, para que el token legacy y la sesión convivan sin redirects ni `403`.
- **Filtro propio de proyectos.** Cubre exclusivamente `/api/admin/projects/**`. Acepta (a) una `WebSession` con el atributo de administrador o (b) `X-Sgdev-Portfolio-Admin-Token`/`Bearer` igual a `PORTFOLIO_ADMIN_TOKEN` o, como fallback, `PORTFOLIO_USAGE_ADMIN_TOKEN`. Un valor vacío o igual a `change-me-admin-token` nunca autoriza por sí mismo; si `PORTFOLIO_ADMIN_TOKEN` no está configurado, se evalúa el fallback `PORTFOLIO_USAGE_ADMIN_TOKEN`. Sin sesión ni token válido responde `401` JSON, nunca `503`. `/api/admin/usage/**` no pasa por este filtro y conserva su autorización actual.
- **Contraseña y hash.** La contraseña en claro se compara contra `PORTFOLIO_ADMIN_PASSWORD`; si existe `PORTFOLIO_ADMIN_PASSWORD_HASH`, este tiene precedencia y se valida con BCrypt. Sin ninguno, el login siempre devuelve `401` y el backend arranca. El mensaje es idéntico para usuario inexistente, contraseña incorrecta y contraseña no configurada; no se registran credenciales.
- **Rutas y navegación.** `StaticRoute` incorpora `/admin` y `/admin/login`; `resolveRoute`, `getPageTitle` y `App.tsx` las resuelven con el base path existente. `/login` se mantiene como alias. No se agrega ningún enlace de admin a `primaryNavItems` ni al footer.
- **Base de autenticación no versionada.** `spring-boot-starter-security`, `SecurityConfig`, `AuthController`, `LoginPage.tsx`, `authClient.ts` y `projectForm.ts` están en el working tree pero no en `HEAD`. No son una dependencia nueva de la unidad: se integran en T-07 junto con el cambio. Cualquier afirmación de “contrato existente en `main`” queda reemplazada por “base en working tree que se commitea en T-07”.
- **Producción ya publicada.** ArgentiCommerce existe publicado, destacado, `sortOrder` 10, `liveUrl:"/argenticommerce/"`, repositorio GitHub, stack Next.js/TypeScript/Spring Boot/PostgreSQL/Flyway/Docker/Nginx, portada 1440×900 y galería. El enlace relativo responde `200`. No se vacía, no se sobrescribe y “Ver en producción” es el comportamiento correcto. La verificación es de lectura; las pruebas de escritura usan un proyecto descartable.
- **Datos del seed para base vacía.** Título `ArgentiCommerce`, slug `argenticommerce`, resumen y descripción coherentes con el README, `liveUrl:"/argenticommerce/"`, repositorio `https://github.com/Sebas-gatica-dev/Argenticommerce`, stack Next.js/TypeScript/Spring Boot/PostgreSQL/Flyway/Docker/Nginx, estado `published`, destacado, `sortOrder` 10, `infraAppSlug:"argenticommerce"`. Sin imágenes, porque no hay un asset versionado autorizado. La producción existente conserva sus imágenes.
- **Seed no es migración.** Solo inserta si `portfolio_projects` está vacía. Si existe cualquier fila —aunque no esté el slug— no inserta ni actualiza. Es una decisión aceptada porque producción ya contiene ArgentiCommerce. La inserción usa `ON CONFLICT` o captura el duplicado dentro de una transacción, para que dos arranques concurrentes no rompan el inicio.
- **Compatibilidad pública y CORS.** Los endpoints `/api/projects`, `/api/projects/{slug}` y `/api/project-media/{key}` no cambian de forma ni de prefijo. El admin es same-origin a través de Nginx o del proxy local; no se introduce un API cross-origin ni se modifica `CorsConfig` (`allowCredentials=false` sigue siendo correcto para este diseño).

## Dependencias y decisiones operativas

- `backend/src/main/java/dev/sg/portfolio/auth/SecurityConfig.java` hoy exige variables sin default y usa form login; se reduce a `permitAll`, CSRF deshabilitado y sin form login/httpBasic.
- `backend/src/main/java/dev/sg/portfolio/auth/AuthController.java` hoy solo implementa `GET /session` y puede devolver cuerpo vacío para anónimos; debe completar el contrato con `WebSession` y devolver siempre el JSON anónimo.
- El nuevo `WebFilter` de proyectos debe recibir `ServerWebExchange` para leer la `WebSession`, y convivir con `PortfolioAdminAuthorizer`/controlador sin duplicar la decisión. `/api/admin/usage/**` no se toca.
- `src/pages/LoginPage.tsx` postea a `/login` raíz con formulario urlencoded; se reemplaza por el contrato JSON bajo `/portfolio/api/auth/login`. `src/api/authClient.ts` solo tiene `getSession()` y debe incorporar login/logout.
- El panel admin necesita un cliente de proyectos admin; reutiliza los tipos de `src/api/projectClient.ts` y el contrato de `src/features/admin/projectForm.ts`, sin crear dependencias nuevas.
- `docker-compose.yml` debe propagar las variables de admin y el modo de forward headers. El volumen `portfolio_project_media` ya existe y es la garantía de persistencia; no se cambia su nombre ni se borra en producción.
- `nginx/gateway.conf` ya enruta `/portfolio/api/` al backend y `/portfolio/` al frontend. No requiere cambios para login ni admin; se valida que no haga falta una regla adicional.
- CI en `.github/workflows/ci.yml` ya construye el frontend con `VITE_BASE_PATH=/portfolio/`, ejecuta `./mvnw test` y valida Compose; el push a `main` dispara el deploy si `SGINFRA_DISPATCH_TOKEN` está configurado. No se debe excluir `package-lock.json` del control de versiones.
- La contraseña ya fue entregada y no se documenta. La credencial SSH está disponible en `%LOCALAPPDATA%\Packages\OpenAI.Codex_2p2nqsd0c76g0\LocalCache\Local\SGDev\Secrets\personal-vps-ssh.clixml`; puede localizarse con `Get-ChildItem -Recurse $env:LOCALAPPDATA -Filter personal-vps-ssh.clixml`. ## Riesgos materiales y mitigación

| Riesgo | Impacto | Mitigación y comprobación |
| --- | --- | --- |
| Cookie con nombre o `Path` incorrecto bajo `/portfolio`. | Login exitoso pero sesión no enviada; el panel parece desloguearse. | Usar `SESSION`, `Path=/`, `SameSite=Lax`; verificar `Set-Cookie` y `GET /session` con cookie jar en Docker y HTTPS. |
| `Secure` no se activa detrás de Nginx o rompe HTTP local. | Cookie sin `Secure` en producción o login local inutilizable. | `server.forward-headers-strategy=framework`; `Secure` condicionado al scheme HTTPS; probar HTTP local y HTTPS en VPS. |
| Spring Security intercepta con redirect o `403`. | Login/API admin inutilizables. | `SecurityConfig` con `permitAll`, CSRF deshabilitado y sin form login/httpBasic; comprobar ausencia de `Location` y respuestas JSON. |
| Token vacío o placeholder autoriza el API. | Acceso no autorizado con un valor público conocido. | Rechazar vacío y `change-me-admin-token`; usar el fallback de usage solo si el token admin no está configurado; `.env.example` con `PORTFOLIO_USAGE_ADMIN_TOKEN=` vacío; probar token vacío, inválido, válido y fallback. |
| `/api/admin/usage/**` se rompe por el filtro nuevo. | SgInfra pierde acceso a usage. | Excluir usage del filtro; probar `/api/admin/usage/ips` con su token si está configurado. |
| Arranque fallido por variables obligatorias. | Backend caído tras el deploy, incluido el sitio público. | Defaults y credencial opcional; probar arranque sin contraseña; `npm run build:api`. |
| La VPS no recibe `PORTFOLIO_ADMIN_PASSWORD` o SgInfra regenera el entorno. | Backend sano pero login siempre `401`. | Verificar después del deploy; reponer la variable si hace falta; documentar como riesgo residual sin registrar el valor. |
| Seed duplicado, bloqueo por `slug` único o sobrescritura. | Arranque fallido o pérdida de datos. | Insertar solo con tabla vacía; `ON CONFLICT`/captura de duplicado; no actualizar filas; probar doble arranque. |
| Base poblada sin el slug. | El seed no crea ArgentiCommerce. | Aceptado y probado: no inserta ni modifica. Producción ya tiene el registro; no se presenta como migración. |
| Escritura accidental sobre ArgentiCommerce real. | Pérdida de portada, galería o URL. | Verificación pública de solo lectura; pruebas de imagen en proyecto descartable con `kind:"gallery"` y limpieza; nunca borrar volúmenes. |
| Borrado de imagen deja archivo huérfano. | Disco creciente y datos inconsistentes. | Verificar el archivo físico en el volumen tras `DELETE`, no solo el `404` de media. |
| Sesión en memoria perdida en cada redeploy. | Reingreso manual del administrador. | Aceptado para un único usuario; documentado; no se agrega persistencia de sesión. |
| Credencial filtrada en repo, logs o evidencia. | Compromiso de la cuenta admin. | Usar solo variables de entorno; `.env` ignorado; revisar diff y salidas antes del push; no pegar contraseñas en specs ni en `testing.md`. |
| `200` del SPA tomado como prueba de login. | Falso positivo de autenticación. | Validar `/api/auth/session` anónimo y el POST de login, además del `200` de la ruta SPA. |
| Límite de subida insuficiente (5 MB binario → ~6,7 MB base64). | Rechazo en Nginx o en el límite en memoria del backend. | Mantener `client_max_body_size 12m`, el límite de memoria actual y probar una imagen cercana al límite. |
| Base de auth no versionada. | El plan no se reproduce desde un `main` limpio. | Commit explícito de `spring-boot-starter-security`, `SecurityConfig`, `AuthController`, `LoginPage`, `authClient` y `projectForm` en T-07; mantener `package-lock.json` versionado. |

## Entornos y operación

- **Local (Windows):** `npm run build`, `npm run build:api`, `node scripts/mvnw.mjs test`; backend con `npm run dev:api`. Para reproducir el subpath, no confiar en el `.env` (define `VITE_BASE_PATH=/`): usar `$env:VITE_BASE_PATH='/portfolio/'; docker compose up -d --build` en PowerShell o `VITE_BASE_PATH=/portfolio/ docker compose up -d --build` en Bash, y abrir `http://localhost:8080/portfolio/`.
- **Integración:** Compose local con PostgreSQL, backend y Nginx. La contraseña local es desechable y no se reutiliza la de producción. Para el seed se usa una base local nueva o la prueba unitaria; nunca se borra el volumen de producción. La subida de prueba usa un proyecto descartable y `kind:"gallery"`; se limpia al terminar.
- **Destino:** VPS `143.95.217.87:22022` (root; credencial DPAPI localizable según `.agents/skills/sgdev-vps-connection/SKILL.md`), aplicación publicada en `https://sgdev.com.ar/portfolio/`. Se verifica la revisión desplegada, los contenedores activos y los logs de arranque.
- **Datos de prueba:** usuario `sgdev-admin`; contraseña tomada de la variable de entorno del entorno que se prueba, sin imprimirla. ArgentiCommerce de producción: una fila, `liveUrl:"/argenticommerce/"`, portada y galería existentes. Imagen de prueba: PNG de 1×1 en galería de un proyecto descartable; archivo sintético mayor a 5 MB para el rechazo.
- **Verificación de demos:** las cuatro rutas (`/portfolio/demos`, chat, turnos, documentos), al menos health/blueprint del backend y un POST SSE breve con timeout, sin exigir una respuesta completa del modelo. Si el modelo local no está disponible, se registra la degradación esperada y se valida que el contrato SSE no cambie.
- **Recuperación y reversión:** si el deploy deja el backend sin arrancar, se revierte al commit anterior en `main` y se vuelve a disparar `deploy-latest`; si el login falla solo por entorno, se corrige la variable y se reinicia el backend sin volver a desplegar código. El cambio no elimina tablas ni migra datos; no se borran `portfolio_postgres_data` ni `portfolio_project_media`.
